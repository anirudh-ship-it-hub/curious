# Curious — Engineering

## Stack

Next.js, React, TypeScript, Tailwind, Supabase (Postgres + auth + storage), Git/GitHub, Vercel. Deliberately simple: no complex multi-user/collaboration/enterprise infra, no AI agent orchestration frameworks, no vector DB — until a fixed/simple mechanism has demonstrably failed at real usage scale.

## AI pipeline

```
User Question
   -> Safety pre-filter (self-harm/suicide method-seeking; short-circuits to a fixed
      compassionate response + crisis-resource pointer, see "Safety layer" below)
   -> Factoid pre-filter (cheap check; single-fact lookups short-circuit here)
   -> Interpretation call (ONE AI call, structured output):
        content (tree | graph — see "Knowledge content schema" below),
        archetype, complexity, difficulty, importance,
        dependencies (concept graph edges), motif tags,
        core takeaways, follow-up predictions, visual potential
   -> Rendering layer produces Gist / Explore / Make It Stick
      as different VIEWS of the same object (no separate AI calls per depth)
```

Follow-up handling: determine whether the follow-up expands the current concept (expand existing graph/structure) or is unrelated (create a new connected node).

## Knowledge content schema — tree vs. graph

The interpretation object's `content` field is a discriminated union, not flat prose (`docs/decisions.md` §12):
- Process/Mechanism, Timeline/Historical, Comparison, Hierarchy/Structure, Open-ended/Conceptual → **tree** (root node + nested children: label, detail, children).
- Causal, System → **graph** (nodes + typed edges, e.g. "leads to," "feeds back into") — the only shape that can express one cause driving multiple effects or a feedback loop, which a tree structurally cannot.

How much of the tree/graph renders at Gist vs. Explore depth is still open (§12).

## Safety layer

Two layers, ahead of the rest of the pipeline (`docs/decisions.md` §13):
1. **Dedicated pre-filter** — cheap classification call, scoped to self-harm/suicide method-seeking only (not a general harm/violence classifier). Flags method-seeking questions distinctly from legitimate psychological/causal curiosity about the topic, and short-circuits to a fixed compassionate response with a crisis-resource pointer.
2. **Refusal backstop** — catches the underlying provider's own refusal (e.g. for weapons/violence instruction-seeking, deliberately outside the pre-filter's scope) and maps it to the same safe response instead of a generic error.

Validated against real harmful queries (correctly short-circuited, no harmful content generated) and a legitimate control question (correctly not flagged).

**Bug found and fixed (2026-09-18)**: the refusal backstop originally matched on the AI SDK's generic "failed to generate JSON" error *message*, which fires for any malformed/truncated model response, not just genuine refusals. During a rate-limited seeding batch this misclassified a benign question ("python vs javascript for a beginner") as a safety refusal, silently returning the crisis-helpline message instead of real content — confirmed by reproducing the same question cleanly 3/3 outside the rate-limited batch.

Fixed in `src/lib/ai/interpret.ts` to check the model's actual raw output instead of pattern-matching the error message. Two shapes carry it depending on how the failure surfaces: `NoObjectGeneratedError.text` (AI SDK's own wrapping), or — what Groq's weapons-refusal case actually throws — an `APICallError` (HTTP 400, `json_validate_failed`) whose response body carries the model's raw refusal text under `error.failed_generation`. A genuine refusal now requires that text to actually read as refusal prose ("I'm sorry, I can't help with that…"); a truncated/malformed JSON response does not, so it correctly rethrows as a real error instead of being swallowed into a wrong "safety" result. Hit one follow-on bug while fixing this: the regex checking for refusal prose used straight apostrophes, but models routinely write "I'm"/"can't" with a curly apostrophe (U+2019) — silently never matched until normalized. Re-validated: full `eval:safety` 4/4 (both self-harm cases, the weapons backstop, and the legitimate control question all correct), plus the original misfire question re-confirmed clean.

Make It Stick: existing knowledge object -> user types an explanation -> rubric-check against 2-4 pre-defined core takeaways (structured covered/missed + confidence per point, not open holistic grading) -> feedback.

## Archetypes (locked list — 7)

Process/Mechanism, Causal, Timeline/Historical evolution, Comparison, System, Hierarchy/Structure, Open-ended/Conceptual (catch-all — classifier must justify rejecting 1-6, or emit low confidence, before defaulting here). Separate `intent` metadata tag (understand / practical-do / decide) captures the practical/decision dimension without forking the archetype.

## Recommendation engine

- Relevant: content-based match on motif tags (closed taxonomy, ~15-20 tags, tagged for free in the interpretation call).
- Adjacent: one-hop traversal of the concept-dependency graph.
- Wildcard / explore-exploit: epsilon-greedy bandit. Epsilon starts ~50% for new users, decays toward ~15-20% as query history accumulates. Reward = engagement (click, read-through, follow-up = positive; bounce = negative).
- No embeddings/vector DB for the beta. Plain Supabase tables: per-user motif counts (recency-weighted), concept-dependency edges, recommendation-shown/engaged log.
- Candidate pool = shared across all beta users (any user's asked questions are readable as recommendation candidates, not siloed per-user) plus a curated seed set for cold start, run through the same interpretation pipeline so seed content matches organic content's shape exactly.

**Built 2026-09-15** (`src/lib/recommend/{scoring,candidates,bandit}.ts`, `src/app/api/recommendations/route.ts`) — implementation notes, all tunable/build-and-tune status like the depth thresholds above, not locked mechanism changes:
- Scoring is done in-process (TypeScript), not SQL-side: the shared pool (capped at 300 rows) is fetched once per request via the service-role client, then relevant/adjacent/wildcard are ranked in memory. Deliberately simple per the "no vector DB, no embeddings infra" constraint — revisit only once a real pool size makes in-memory ranking the actual bottleneck.
- "Adjacent" cannot literally traverse `concept_edges` cross-user, since edges only ever connect a single user's own question rows (by construction — see `supabase/schema.sql`). Implemented instead as substring matching between a candidate's question text and the current user's own recent `dependencies` entries — same underlying data ("concepts the user was just pointed toward"), without needing embeddings.
- No slot backfilling: if a user's "relevant" queue is empty (e.g. a cold-start user with no motif history yet), that slot is simply not filled rather than silently substituted with a different candidate type. Keeps `recommendation_log.slot` honest for later analysis, at the cost of sometimes returning fewer than the requested batch size.
- Already-shown candidates (all-time, per user, from `recommendation_log`) are excluded from every future pool fetch so the same item is never recommended twice.
- **Pool exhaustion** (docs/decisions.md §10 addendum, built 2026-09-18): `GET /api/recommendations` returns `poolExhausted: true` when the combined relevant+adjacent+wildcard pool is genuinely empty for a user (not just "this batch's assigned slots came up empty," which is a separate, non-exhausted case returning `poolExhausted: false`). Alongside it, returns `recentlyExplored` — the user's own questions from the last rolling 24h, id/question/coreTakeaways only — for the client to render the "caught up for today, here's what you looked at, try explaining one out loud" end state. No UI consumes this yet.
- `PATCH /api/recommendations` records click/follow-up engagement and recomputes `computeReward`. **Built 2026-09-18**: it now also implements §11's thumbs-routing for recommended content — a `thumbsUp` in the request body updates `recommendation_log.thumbs_up` and writes a net adjustment to `motif_counts` (reads the question's `motif_tags` server-side via the admin client, §14-compliant, never returned to the caller). Net, not absolute — flipping thumbs up→down applies a -2 swing (now -8, since the nudge magnitude changed — see below), not a fresh nudge, and re-sending the same value is a no-op, so toggling never double-counts. `incrementMotifCounts` floors at 0 (a negative count has no meaning). Self-asked-content thumbs is the mirror case, `POST /api/content-feedback` — structurally separate (writes to `content_feedback`, one row per (user, question) via a unique constraint, never touches `motif_counts`), and only accepts a `questionId` the caller owns.

**2026-09-22 — motif taste model: windowed recency, not decay; thumbs magnitude resized** (`docs/decisions.md` §19): relevant-slot weighting (`motifWeights` in `candidates.ts`) is now all-time count (`motif_counts`, unchanged) **plus** a recent-window tally (`tallyMotifs()` in `scoring.ts`) over the user's own last 20 asked questions — additive, not a decay-based replacement. A motif with real history but no recent activity still scores via its all-time weight; a motif that's brand-new but currently dominant now scores too, via the window, even with zero all-time count (previously invisible to relevant-slot scoring until it accumulated enough history to make the all-time top-5 cut — a real gap this closes). Window size (20) is a forgiving parameter deliberately chosen over a decay half-life, which isn't: get a half-life wrong and the whole system breaks in one of two directions depending on real usage cadence that doesn't exist yet; get a window size a bit off and the recency signal is just somewhat more or less sensitive than ideal. `THUMBS_MOTIF_NUDGE` raised from 1 to 4 — sized as a multiple of the organic unit that already exists (one asked question contributes +1 per motif), not an unrelated invented number. Extended `npm run eval:recommend` with `tallyMotifs` unit tests plus an additive-combination scenario test; live-validated against the real API with a seeded account confirming both the previously-invisible fresh-motif case and the thumbs-magnitude change.

**Thumbs feedback routing** (`docs/decisions.md` §11) — a thumbs up/down on any piece of content routes differently depending on content type, not uniformly:
- On **recommended** content (Drift, Discover) → writes a small adjustment to the same per-user motif-count store that "questions asked" already writes to. Real taste signal, since the person didn't ask for it.
- On **self-asked** content → does NOT touch the motif-taste model (down-voting your own answer isn't evidence against the topic you sought out). Routes to a separate content-quality signal instead, for eval-set review and beta check-ins.
- Either way, `computeReward` in `bandit.ts` is unaffected — it already consumes `thumbsUp` as the reward for that specific recommendation instance; this is an additional write path on top.

## Drift

Bite-sized (Gist-depth) scrollable feed surfacing recommendation-engine output (`docs/decisions.md` §10) — no new content-generation mechanism, no new AI call shape. Content generation is **just-in-time with a small prefetch buffer** (next 1-2 cards generated while the current one is showing), not eager whole-batch generation — avoids paying AI cost for cards scrolled past unread. Session length and scrolls-per-session/day are logged as a **canary-only signal** (beta check-ins), explicitly never fed into the bandit and never a KPI — the recommendation engine's reward function is unchanged by this feature.

## Beta metrics (`docs/decisions.md` §5)

**Built 2026-09-18** (`scripts/beta-metrics.ts`, `npm run metrics`) — a plain report, not a dashboard, matching the "review manually at weekly check-ins" precedent already established for reviewing recommendation quality. Covers all six short-term diagnostic KPIs:
- **Curiosity Continuation Rate** — no session-boundary concept exists in the schema, so this is measured per-question (% of a user's own questions with ≥1 outgoing `concept_edges` row) rather than per-session. A named proxy, not the literal locked definition — revisit if/when session boundaries become real infrastructure.
- **Knowledge Expansion Rate** — distinct questions asked, per user.
- **Recommendation acceptance rate** — click/follow-up/thumbs rates and average reward from `recommendation_log`.
- **Depth-selection distribution** — required new instrumentation: `depth_views` (one row per user/question/depth, upserted so tab-toggling doesn't inflate counts), since `questions.depth_recommendation` only captures what the AI suggested, never what was actually looked at. Wired into both the ask screen (`useEffect` on `activeDepth` change) and Drift (card mount = Gist, expand = Explore, Make It Stick toggle = Stick) via a shared `src/lib/log-depth-view.ts` fire-and-forget helper.
- **AI cost per user** — required new instrumentation: `questions.total_tokens`, summed across every `generateObject` call a single `interpret()` invocation makes (safety pre-filter + factoid pre-filter + full interpretation). Reported as raw tokens, not a fabricated `$` figure — Groq is the free-tier default, so a dollar conversion would currently just mean $0 regardless of usage. Make It Stick's evaluation call isn't included (no persistence table for those attempts exists) — a known, flagged gap.
- **Raw per-user activity traces** — questions, a session count (heuristic: >30min gap between consecutive questions = new session, tunable placeholder like the depth/bandit constants), and distinct days active. Deliberately not DAU/WAU/MAU percentages (§5: noise at n=10).

Validated against a real fixture (real `interpret()` calls, real token counts, a real follow-up edge, real depth views) before being trusted — all six numbers matched what was actually inserted.

## Reliability discipline

Do not trust a single unconstrained AI call for anything downstream systems depend on:
- Structured output (schema-constrained) for every classification/tagging call, never prose parsing.
- Hand-labeled eval sets for classification tasks (archetype, motif) before shipping prompt changes.
- Deterministic computation wherever possible instead of AI self-report (e.g. read time from actual word count).
- Reward signals for the bandit come from logged behavior, not AI judgment.

## Cost philosophy

One rich AI generation call per question/follow-up, not one call per depth. Additional calls only for genuinely dynamic needs (new information, follow-up expansion, Make It Stick evaluation, safety pre-filter). Target: essentially zero cost for a ~10-person beta — provider defaults to Groq (`AI_PROVIDER` env var), with DeepSeek/Anthropic as drop-in swaps behind the same interface (`src/lib/ai/provider.ts`); not re-evaluated against real cost/latency data yet, but no longer blocking.

**2026-09-22 — recommendation batch size derived, not guessed** (`docs/decisions.md` §18): `DEFAULT_BATCH_SIZE` in `src/app/api/recommendations/route.ts` is now `computeDefaultBatchSize()` — reading-speed research (Brysbaert 2019, 238 wpm) applied to a *measured* real average Gist-card length (70.4 words, n=16), against a target uninterrupted-scroll buffer, clamped to a working-memory-derived sanity floor `[4, 8]`. Currently computes to 6. Three other research strands considered and explicitly NOT used as direct evidence for this number (kept honest rather than stretched): Cowan's chunk-capacity figure (sanity floor only), interleaving research (supports the relevant/adjacent/wildcard mixing strategy, not batch size), vigilance-decrement research (supports the existing §10 session-length canary, not per-fetch sizing).
